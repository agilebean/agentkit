# Robotic wording inventory

The instances behind RULES.md rule 2, in one table. Compiled 2026-10-03 from the KUBS DT folder logs (Course Design, S1 to S4), the session record of 2026-08-06 to 2026-10-03, and the RULES.md history. The record has a gap from 2026-09-10 to 2026-09-23 (cleaned up on 09-25); the folder logs cover that window.

The user, 2026-10-03: "i gave hundreds of examples the last 3 weeks of robotic wording ... i had instructed that you keep an inventory and not only for kubs so you learn what is robotic and how to improve it!"

The standard behind every row: anything the user will read or hear must be understood on the first pass, without a pause and without asking what it means (RULES.md rule 48's test). The markers are the failures seen so far, not the whole standard.

## The system

- `RULES.md` rule 2: the standing classes, each with the plain fix. The reference for the word "robotic".
- This file: one table, one row per instance: location and date, the flagged wording, why the user rejected it, the repair, and why the repair is better.
- Checker: `robot_markers.tsv` (this folder) holds the machine-checkable subset; `scripts/wording_lint.py` runs it on any file, in any project. The KUBS pipeline wraps it (`pipeline.py lint --session N`).

Maintenance: every new correction is appended at the end of the table in the same turn as one row: location and date, the flagged words, why the user rejected them (the user's words where the record has them), the repair, and why the repair is better. Keep cells short: quotes are trimmed to the carrier fragment, one or two sentences per cell. A correction without the reasoning is incomplete; when the exchange carries none and the reason is not evident, ask before appending. A new class becomes a bullet in rule 2; a class a machine can catch becomes a row in `robot_markers.tsv`, checked by `scripts/wording_lint.py`.
